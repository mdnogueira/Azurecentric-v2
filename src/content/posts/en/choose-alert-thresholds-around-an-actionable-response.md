An alert rule is a commitment to act. If the threshold fires but no one can resolve the issue, or if the signal is too noisy to distinguish from normal variance, the alert has failed its primary purpose. The first question when designing a threshold is not "What value indicates a problem?" but "What specific action will we take when this fires, and is that action feasible within the evaluation window?"

Azure Monitor provides two distinct alert types: metric alerts for numerical data points and log search alerts for structured log events. Both allow you to define conditions, but the mechanics of threshold calculation and the resulting noise profile differ significantly. Choosing the right threshold model depends on whether you have a fixed business limit or a dynamic operational baseline.

## Static thresholds require a defined business limit

Static thresholds are appropriate when you have a hard constraint that must not be exceeded. Examples include storage account capacity limits, API rate limits, or a maximum acceptable latency for a specific transaction type. In these cases, the threshold value is derived from business requirements or architectural specifications, not from historical data analysis.

When configuring a static threshold, you must select an aggregation type and a frequency of evaluation that align with your response capability. The documentation states that you can select aggregation functions such as Sum, Count, Average, Min, or Max for metric alerts [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). For log search alerts, you can measure table rows or calculate a numeric column [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule).

A common mistake is setting the frequency of evaluation too high relative to the time it takes to remediate. If an alert fires every minute but your runbook requires ten minutes to restart a service, you will receive ten identical alerts before the first one is addressed. This leads to alert fatigue and obscures new issues. The documentation notes that for stateless metric alerts with a frequency of less than five minutes, notifications are sent between one and six minutes while the condition persists [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). For frequencies above five minutes, the interval doubles. This behaviour confirms that high-frequency evaluation generates high-volume noise if the underlying condition is persistent.

To reduce noise for static thresholds, use the "Number of violations" setting. This advanced option allows you to specify that an alert should only trigger if a certain number of violations occur within a specific evaluation period [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). For example, you might require three consecutive five-minute periods of high CPU usage before triggering a scale-out action. This ensures that transient spikes do not trigger costly or disruptive operations.

## Dynamic thresholds for variable workloads

Dynamic thresholds use machine learning algorithms to learn historical metric behaviour and calculate appropriate upper and lower bounds. They are recommended for metrics that exhibit regular patterns, such as virtual machine CPU percentage or Application Insights HTTP request execution time [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). The primary advantage is scalability: you can create a single alert rule for hundreds of metric series without manually tuning thresholds for each instance.

Dynamic thresholds are particularly useful for noisy metrics like machine CPU or memory [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). They help prevent noisy (low precision) or wide (low recall) thresholds that do not have an expected pattern [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds).

However, dynamic thresholds have specific data requirements. The system uses ten days of historical data to calculate hourly or daily seasonal patterns upon creation [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). It requires at least three weeks of data to detect weekly seasonality [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). Crucially, dynamic thresholds do not trigger an alert before collecting three days and at least 30 samples of metric data [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). This means you cannot use dynamic thresholds for new resources or resources that have recently changed behaviour if immediate alerting is required.

The sensitivity setting controls how closely the threshold follows the metric series. High sensitivity triggers alerts on the smallest deviation, resulting in more alerts. Low sensitivity allows greater deviation, resulting in fewer alerts [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). If a dynamic threshold rule is too noisy, you should reduce the sensitivity to Medium or Low, or use the "Number of violations" setting to require multiple deviations before triggering [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds).

Dynamic thresholds are good for detecting significant deviations, as opposed to slowly evolving issues. Slow behaviour changes probably won't trigger an alert [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds). If your metric exhibits large fluctuations or irregular behaviour, the dynamic model may build wide bounds, resulting in missed alerts. In such cases, consider monitoring a complementary metric, such as success rate instead of failure rate [Create an Azure Monitor metric alert with dynamic thresholds](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-dynamic-thresholds).

## Log search alerts for complex conditions

Log search alerts allow you to define conditions based on KQL queries. This is essential for scenarios where no single metric captures the issue, such as detecting a specific error pattern in application logs or a combination of resource states.

When configuring a log search alert, you must define a query that returns the log events for which you want to create an alert [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule). The query results are transformed into a number, which is then compared against a threshold value using an operator [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule). You can measure the number of returned rows or calculate a numeric column from the results [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule).

A critical consideration for log search alerts is the identity used for authentication. If you do not use a managed identity, the alert rule permissions are based on the permissions of the last user who edited the rule [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule). This can lead to unexpected failures if the user loses access or if the rule is edited by someone with insufficient permissions. Using a system-assigned or user-assigned managed identity is recommended to ensure consistent access to the Log Analytics workspace or Azure Data Explorer cluster [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule).

Log search alerts also support splitting by dimensions. This allows you to monitor specific time series, such as individual virtual machines or API names, and fire separate alerts for each dimension value that meets the condition [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). If you select more than one dimension value, each time series that results from the combination triggers its own alert and is charged separately [Create Azure Monitor metric alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-metric-alert-rule). This is useful for granular monitoring but increases cost and potential noise if not managed carefully.

The frequency of evaluation for log search alerts can be set from one minute to one day [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule). However, there are limitations when using a frequency of one minute. The internal manipulation performed to optimize the query can cause it to fail if it contains unsupported operations, such as `search`, `union`, or `take` (limit) [Create Azure Monitor log search alert rules](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule). If your query fails at one-minute frequency, you must increase the evaluation interval or refactor the query.

## Verification and next actions

Before deploying an alert rule, verify that the threshold aligns with your response capability. For static thresholds, confirm that the "Number of violations" setting prevents transient spikes from triggering actions. For dynamic thresholds, ensure the resource has sufficient historical data and that the sensitivity level matches the desired noise profile. For log search alerts, test the query with the intended frequency to ensure it does not fail due to unsupported operations.

Finally, define the action group associated with the alert rule. The action should be specific, automated where possible, and assigned to a team that has the authority and knowledge to resolve the issue. An alert without a clear, actionable response is merely a notification, not a monitoring solution.
